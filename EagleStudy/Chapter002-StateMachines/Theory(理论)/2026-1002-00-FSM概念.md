# FSM（有限状态机）的程序设计概念

**FSM（Finite State Machine，有限状态机）**是一种非常重要的程序设计思想。

它解决的问题可以简单概括为：

> **一个程序在不同“状态”下，面对不同条件，应该做什么？什么时候从一个状态切换到另一个状态？**

在游戏开发中尤其常见，例如：

* 玩家：待机 → 行走 → 奔跑 → 跳跃 → 攻击
* 敌人：巡逻 → 发现玩家 → 追击 → 攻击 → 死亡
* UI：关闭 → 打开 → 加载 → 显示 → 关闭
* 游戏流程：开始 → 游戏中 → 暂停 → 胜利/失败

---

# 一、什么是“状态”

首先理解 **State（状态）**。

状态就是：

> **描述一个对象当前处于什么行为阶段。**

例如一个敌人：

```text
巡逻
追击
攻击
受伤
死亡
```

这些都是状态。

假设敌人当前处于：

```text
追击
```

那么它此时应该执行：

```text
向玩家移动
```

如果距离玩家足够近：

```text
追击 → 攻击
```

如果玩家消失：

```text
追击 → 巡逻
```

如果敌人生命值 ≤ 0：

```text
追击 → 死亡
```

所以：

```text
状态 = 当前应该执行什么行为
```

---

# 二、FSM的三个核心概念

一个最基本的有限状态机可以抽象成：

```text
State
Transition
Condition
```

也就是：

```text
状态
状态转换
转换条件
```

例如：

```text
        玩家进入攻击范围
              ↓
[巡逻] ─────────→ [攻击]
   ↑                │
   │                │ 玩家离开范围
   └────────────────┘
```

这里：

* `巡逻` = 状态
* `攻击` = 状态
* `玩家进入攻击范围` = 条件
* `巡逻 → 攻击` = 状态转换

---

# 三、状态机的基本结构

可以把 FSM 看成一个数学模型：

```text
FSM = 状态集合 + 输入 + 转换规则 + 当前状态
```

例如：

```text
状态：

Idle
Move
Attack
Dead
```

输入：

```text
玩家距离
生命值
玩家是否存在
攻击冷却
```

转换规则：

```text
Idle → Move
Move → Attack
Attack → Move
任何状态 → Dead
```

最终程序不断进行：

```text
读取当前状态
      ↓
读取环境/输入
      ↓
判断转换条件
      ↓
是否需要切换状态？
   ↓          ↓
  是          否
   ↓          ↓
切换状态     继续当前状态
   ↓
执行状态行为
```

# 四、最简单的FSM

例如设计一个角色：

```text
Idle
Move
Jump
```

状态转换：

```text
             按下移动键
        ┌───────────────→
     [Idle]             [Move]
        ↑                  │
        │                  │ 松开移动键
        └──────────────────┘

[Idle] ──按跳跃──→ [Jump]

[Move] ──按跳跃──→ [Jump]

[Jump] ──落地────→ [Idle]
```

这就是一个非常典型的 FSM。

---

# 五、程序中的核心：CurrentState

FSM通常都会有一个非常重要的变量：

```csharp
CurrentState
```

表示：

> **当前状态是什么。**

例如：

```csharp
State currentState = State.Idle;
```

然后每一帧：

```csharp
switch (currentState)
{
    case State.Idle:
        UpdateIdle();
        break;

    case State.Move:
        UpdateMove();
        break;

    case State.Jump:
        UpdateJump();
        break;
}
```

这就是最原始的状态机。

---

# 六、状态切换

状态机真正重要的地方是：

```text
Transition
```

例如：

```csharp
if (Input.GetKeyDown(KeyCode.Space))
{
    currentState = State.Jump;
}
```

本质就是：

```text
当前状态
    ↓
检测条件
    ↓
修改 CurrentState
```

例如：

```text
Idle
 ↓
按下 Space
 ↓
Jump
```

---

# 七、不要把“状态”和“条件”混在一起

这是学习 FSM 时非常重要的一点。

例如：

```csharp
if (playerDistance < 2)
{
    Attack();
}
```

这只是一个条件判断。

而 FSM 思维是：

```text
当前状态：Chase

条件：
playerDistance < 2

结果：
Chase → Attack
```

也就是说：

**条件负责决定“去哪”。**

**状态负责决定“做什么”。**

这是 FSM 最核心的思想之一。

---

# 八、状态通常具有三个生命周期

一个比较完整的 State 通常有：

```text
Enter
Update
Exit
```

也就是：

```text
进入状态
 ↓
持续执行
 ↓
离开状态
```

例如敌人进入攻击状态：

```text
Enter
↓
播放攻击动画
↓
Update
↓
等待攻击时机
↓
造成伤害
↓
检测是否继续攻击
↓
Exit
↓
停止攻击动画
```

可以写成：

```csharp
class AttackState
{
    public void Enter()
    {
        // 进入攻击状态
    }

    public void Update()
    {
        // 持续执行攻击逻辑
    }

    public void Exit()
    {
        // 离开攻击状态
    }
}
```

---

# 九、为什么需要 Enter / Update / Exit

假设没有 Enter 和 Exit。

所有东西都写在 Update：

```csharp
if (state == Attack)
{
    PlayAttackAnimation();

    if (...)
    {
        DealDamage();
    }
}
```

那么：

```text
PlayAttackAnimation()
```

可能每一帧都调用。

而使用生命周期：

```text
Enter
    ↓
播放一次攻击动画

Update
    ↓
持续处理攻击

Exit
    ↓
清理攻击状态
```

结构会更加清晰。

# 十、FSM最重要的设计思想：职责分离

例如一个敌人有：

```text
巡逻
追击
攻击
逃跑
死亡
```

不要把所有代码写在：

```csharp
Enemy.Update()
```

里面。

否则很容易变成：

```csharp
if (dead)
{
    ...
}
else if (distance < 2)
{
    ...
}
else if (distance < 10)
{
    ...
}
else
{
    ...
}
```

随着游戏复杂度增加：

```text
几十个 if
几十个条件
大量互相影响
```

最终会变成所谓的：

> **状态逻辑泥潭**

FSM的目的就是把它拆开。

# 十一、传统FSM结构

例如：

```text
Enemy
│
├── IdleState
├── PatrolState
├── ChaseState
├── AttackState
├── HitState
└── DeadState
```

每个 State 负责自己的行为。

例如：

```text
PatrolState
    ↓
负责巡逻

ChaseState
    ↓
负责追击

AttackState
    ↓
负责攻击

DeadState
    ↓
负责死亡
```

Enemy本身负责：

```text
管理状态
提供公共数据
执行状态切换
```

# 十二、一个简单的Unity C# FSM

例如：

```csharp
public enum EnemyState
{
    Idle,
    Chase,
    Attack,
    Dead
}
```

然后：

```csharp
public class Enemy : MonoBehaviour
{
    public EnemyState CurrentState;

    void Update()
    {
        switch (CurrentState)
        {
            case EnemyState.Idle:
                UpdateIdle();
                break;

            case EnemyState.Chase:
                UpdateChase();
                break;

            case EnemyState.Attack:
                UpdateAttack();
                break;

            case EnemyState.Dead:
                UpdateDead();
                break;
        }
    }
}
```

然后：

```csharp
void UpdateIdle()
{
    if (playerDetected)
    {
        CurrentState = EnemyState.Chase;
    }
}
```

```csharp
void UpdateChase()
{
    MoveToPlayer();

    if (distance < attackDistance)
    {
        CurrentState = EnemyState.Attack;
    }
}
```

```csharp
void UpdateAttack()
{
    Attack();

    if (distance > attackDistance)
    {
        CurrentState = EnemyState.Chase;
    }
}
```

这样已经是一个完整的基础 FSM。

# 十三、进一步抽象：State接口

当项目变大，可以把 State 独立成对象。

例如：

```csharp
public interface IState
{
    void Enter();
    void Update();
    void Exit();
}
```

然后：

```csharp
public class IdleState : IState
{
    public void Enter()
    {
    }

    public void Update()
    {
    }

    public void Exit()
    {
    }
}
```

攻击状态：

```csharp
public class AttackState : IState
{
    public void Enter()
    {
        // 开始攻击
    }

    public void Update()
    {
        // 攻击逻辑
    }

    public void Exit()
    {
        // 结束攻击
    }
}
```

FSM：

```csharp
public class StateMachine
{
    private IState currentState;

    public void ChangeState(IState newState)
    {
        currentState?.Exit();

        currentState = newState;

        currentState?.Enter();
    }

    public void Update()
    {
        currentState?.Update();
    }
}
```

这样：

```text
StateMachine
     │
     ├── IdleState
     ├── ChaseState
     ├── AttackState
     └── DeadState
```

形成比较清晰的结构。

# 十四、FSM实际上是在管理“行为流程”

可以把它理解成：

```text
普通程序
    ↓
按照代码顺序执行
```

而 FSM：

```text
根据当前状态
    ↓
根据环境输入
    ↓
决定下一状态
    ↓
执行对应行为
```

所以 FSM特别适合：

> **行为具有明确阶段和明确转换关系的问题。**

# 十五、FSM和if-else有什么区别？

这是一个非常值得理解的问题。

实际上：

```text
FSM ≠ 完全不用 if
```

FSM内部仍然会大量使用：

```csharp
if
switch
```

真正的区别在于：

### 普通if-else

重点是：

```text
条件判断
```

例如：

```csharp
if (hp <= 0)
{
    Die();
}
else if (distance < 2)
{
    Attack();
}
else
{
    Chase();
}
```

### FSM

重点是：

```text
状态管理
```

例如：

```text
CurrentState = Chase

ChaseState
    ↓
检测距离
    ↓
距离 < 2
    ↓
切换 AttackState
```

所以：

> **FSM不是一种特殊语法，而是一种组织程序逻辑的方法。**

# 十八、FSM的一个关键问题：状态爆炸

FSM虽然好用，但不是万能的。

假设角色有：

```text
Idle
Move
Run
Jump
Fall
Attack
Hit
Dead
Dodge
Block
Skill
...
```

如果每个状态之间都存在大量转换：

```text
Idle → Move
Idle → Jump
Idle → Attack
Idle → Dodge

Move → Idle
Move → Jump
Move → Attack
Move → Dodge

Jump → Fall
Jump → Attack
Jump → Dodge
...
```

状态数量增加后，转换关系可能急剧增加。

这就是：

> **State Explosion（状态爆炸）**

# 十九、FSM → HFSM

当普通 FSM 变复杂，可以进一步使用：

> **HFSM（Hierarchical Finite State Machine）层次有限状态机**

例如：

```text
Character
│
├── Ground
│   ├── Idle
│   ├── Walk
│   ├── Run
│   └── Attack
│
├── Air
│   ├── Jump
│   └── Fall
│
└── Dead
```

这里：

```text
Ground
Air
Dead
```

本身就是大的状态。

Ground里面又有：

```text
Idle
Walk
Run
Attack
```

这样就能减少大量转换。

# 二十、FSM和行为树的区别

游戏AI中经常会遇到：

```text
FSM
Behavior Tree
Utility AI
GOAP
```

FSM：

> **非常适合明确的状态流程。**

例如：

```text
巡逻 → 发现 → 追击 → 攻击
```

行为树：

> **更适合复杂的决策逻辑。**

例如：

```text
是否能攻击？
├── 能
│   ├── 是否在攻击距离？
│   └── 是否有弹药？
│
└── 不能
    ├── 是否看到玩家？
    └── 是否需要搜索？
```

所以可以简单理解为：

```text
FSM
↓
“我现在处于什么阶段？”

Behavior Tree
↓
“我现在应该选择什么行为？”
```

二者也可以组合使用。

# 二十一、从程序设计角度理解FSM

FSM最重要的不是记住：

```text
State
Enter
Update
Exit
Transition
```

而是理解下面这个思想：

```text
复杂系统
    ↓
拆成有限个状态
    ↓
每个状态拥有明确职责
    ↓
规定状态之间允许的转换
    ↓
根据输入决定转换
```

也就是：

> **把一个复杂的连续行为问题，转换成一个有限的、可管理的离散状态系统。**

---

# 二十二、用一句话理解FSM

可以把 FSM 记成：

```text
FSM = 当前状态 + 输入条件 + 状态转换 + 状态行为
```

例如：

```text
             玩家距离
                ↓
        ┌──────────────┐
        │   状态机     │
        └──────┬───────┘
               ↓
       ┌───────┴───────┐
       ↓               ↓
    Chase            Attack
       │               │
       └───────┬───────┘
               ↓
          CurrentState
```

而从游戏程序架构的角度，最值得掌握的一条原则是：

> **状态决定“现在做什么”，转换条件决定“什么时候换状态”。**

如果你正在学习 **Unity C# 游戏开发**，下一步最值得深入的是 **“如何设计一个通用 FSM 框架”**：从 `IState → StateMachine → Transition → StateContext` 一步一步构建，并最终做成可以复用于玩家、怪物、Boss、UI 的框架。
